### Tolerance, stated up front

* **Discrete counts** (`correct`, `n`, `probe_tokens`, `label_counts`, `majority_class_accuracy`):
  **exact equality, no tolerance.** Accuracy moves in steps of `1/20 = 0.05`; any non-zero difference
  is a different number of correctly answered items, not noise.
* **Probabilities** (`p_gold`, `pred_p`): agreement if `|Δ| ≤ 1e-4`. The stored values are rounded to
  5 dp (≤ 5e-6 of rounding) and my re-run is bit-identical; **observed max |Δ| = 0.000000** over all
  200 diagnostic items in probes B and C.
* **Latency**: excluded from verdicts — it depends on machine load and other agents' jobs. Reported
  as a ratio; my refresher run was **1.07×–1.40× slower** than the stored one on the baseline and
  0.96×–1.52× on the diagnostic, i.e. same order, no contradiction. No claim in either artifact
  depends on a latency comparison.

## 3. Measurement integrity (the substance of the task)

### 3.1 Check 1 — does `place()` put the needle where the label says?

**Yes, exactly.** I re-tokenized every constructed document with `return_offsets_mapping` and located
the first *whole* token of the needle (`experiments/V-001/measure.py`, raw per-item table in
`experiments/V-001/needle_positions.tsv`).

| probe | pad | frac label | needle position label = `int(pad·frac)` | **actual needle token, doc-relative** | **actual, model-sequence** | realized fraction (needle/doc) | items off label |
|---|---|---|---|---|---|---|---|
| A_dtype | 4000 | 1.0 | 4000 | **4000** | 4050 | 0.9938–0.9970 | 0/20 |
| B_position | 4000 | 0.0 | 0 | **0** | 50 | 0.0000 | 0/20 |
| B_position | 4000 | 0.25 | 1000 | **1000** | 1050 | 0.2484–0.2493 | 0/20 |
| B_position | 4000 | 0.5 | 2000 | **2000** | 2050 | 0.4969–0.4986 | 0/20 |
| B_position | 4000 | 0.75 | 3000 | **3000** | 3050 | 0.7453–0.7478 | 0/20 |
| B_position | 4000 | 1.0 | 4000 | **4000** | 4050 | 0.9938–0.9970 | 0/20 |
| C_length | 0 | 1.0 | 0 | **0** | 50 | 0.0000 | 0/20 |
| C_length | 1000 | 1.0 | 1000 | **1000** | 1050 | 0.9756–0.9881 | 0/20 |
| C_length | 2000 | 1.0 | 2000 | **2000** | 2050 | 0.9877–0.9940 | 0/20 |
| C_length | 4000 | 1.0 | 4000 | **4000** | 4050 | 0.9938–0.9970 | 0/20 |
| C_length | 7000 | 1.0 | 7000 | **7000** | 7050 | 0.9964–0.9983 | 0/20 |

Three caveats, none of which breaks the construction:

1. **The denominator is not `pad`.** The document is `pad` filler tokens **plus** the request
   (12–25 tokens, language-dependent), so the realized fraction is always slightly below the label
   (0.25 → 0.2484–0.2493; 0.75 → 0.7453–0.7478). The label means "needle at token `pad·frac` of the
   filler", which is true; it does not mean "at `frac` of the document".
2. **The model sequence starts 50 tokens before the document** — a 45-token question head plus the
   5-token `{"text": "` JSON wrapper (§3.2). So "absolute position" needs +50, not +256 (#9).
3. **In the baseline the request starts one token later than `pad`** — at `pad+1` for all 20 items —
   because `run.py:67` inserts an extra `" "` between filler and request. Harmless, but it means the
   baseline and `place()` do not produce the same document text even though they produce
   **token-id-identical** documents (verified for all 20 requests at all 5 pads).

### 3.2 Check 2 — is `pad` really `pad` tokens?

**The filler prefix is exactly `pad` tokens; the document is not, and neither is the model input.**
Fertility does not distort the prefix, because the prefix is the *same* ASCII filler sentence
repeated and decode→re-encode is prefix-stable — but it does change the total, and the model adds a
wrapper nobody counts.

Measured facts (`measure.json`, `head_probe.json`):

* `FILLER` tokenizes to **43 tokens**; `filler_ids(tok, pad)` is `pad` tokens by construction, and the
  needle's first token lands at exactly `pad` after decode→re-encode (§3.1). **`pad` is real.**
* Request length varies with language: measured tokens per request (i = 0…19) are
  `18,14,15,15,17,14,20,12,15,22,13,21,14,15,15,12,25,16,16,24`. The longest are Hindi i=16 (25),
  Arabic i=19 (24), Portuguese i=9 (22), French i=11 (21); the shortest are Spanish i=7 (12) and
  German i=15 (12). So a `pad=4000` cell is **4012–4025 document tokens**, an intra-cell spread
  of 13 tokens (0.32%). Small, but it means the items in one cell are not the same length.
* **The model input is `45 + 5 + document + 1` tokens.** The `+5` is a JSON wrapper: both scripts call
  `agent.predict({"text": …})`, a dict, and `serialize_state` is `json.dumps` — so the state the model
  encodes is `{"text": "<document>"}`, which costs `▁{"` `text` `":` `▁"` … `▁"}` = 5 tokens.
  Verified end to end: predicted `45+5+23+1 = 69` for request 0 at pad=0, and `repeat.py` recorded
  exactly `69` from `usage.input_tokens`; all 20 items show the same +5 delta. This also explains the
  `+51` offset seen at every non-truncated cell (e.g. pad=7000 → input `7063…7076`).
* **`probe_tokens` is not the model input.** It is `len(tok(document))` for `REQUESTS[0]` only
  (`run.py:68`, `run.py:101`). The other 19 items differ by up to ±7 tokens, and at `limit=1024` the
  model reads 1024 tokens while the row prints up to `7018`.
* The filler is a **single 43-token sentence repeated** ~163× at pad=7000, containing no label word
  and no request content. "Long context" here means "one sentence, many times"; that is a property of
  the probe, and both scripts are honest that it is synthetic.

### 3.3 Check 3 — nondeterminism

**None measurable, in-process or across processes.**

* Same cell twice and three times in one process, 20/20 items: `0/20` predictions differ,
  `max|Δ p_gold| = 0.00000000` (baseline 8192/7000 and 1024/1000; diagnostic C=4000 fp32 and B=0.5 fp32).
* Across processes: the fresh `run.py` output is identical to the stored artifact in every discrete
  field and every `p_gold` in probes B and C.
* The diagnostic internally evaluates the same cell twice under different names
  (`B_position["1.0"]` and `C_length["4000"]` are the same `place(tok, 4000, 1.0, req)`); their
  `per_item` arrays are equal element for element, a free and passing determinism check.
* The 5-token `A`-sweep accuracy agreement (bf16/fp16/fp32 all 0.600) is also a precision-robustness
  signal, though the script discards the per-item rows that would let it be checked properly (#10).

Consequence: every downstream claim can be checked by re-running; nothing here is inside a noise
floor. (The *statistical* floor is a different matter and is the file's own n=20 caveat, which is
correct at ±0.22.)

### 3.4 Check 4 — majority class, and constant-answer collapse

**Majority class, recomputed independently from the label list in the script:** `billing` 9,
`technical` 7, `sales` 4, `other` **0**; `max = 9/20 = 0.450`. Matches the stored value. Trivial
constant classifiers score 0.45 (`billing`), 0.35 (`technical`), 0.20 (`sales`).

**Constant-answer collapse — yes in the baseline, no in the diagnostic.**

* Baseline `limit=1024, pad ∈ {1000,2000,4000,7000}`: the model emits **`technical` for 20/20 items**
  in all four cells (from `repeat.py`, which records the per-item predictions the shipped script
  discards). 0.35 is precisely the `technical`-constant score. `usage.input_tokens` is exactly `1024`
  for all 80 calls.
* Every other baseline cell is mixed (e.g. 8192/7000: `{billing:3, sales:3, technical:14}`).
* Diagnostic: no cell is constant. Prediction histograms — B 0.0 `{billing:11, technical:7, sales:2}`;
  B 0.25 `{technical:15, billing:3, sales:2}`; B 0.5 `{technical:15, billing:2, sales:3}`;
  B 0.75 `{technical:16, billing:3, sales:1}`; B 1.0 `{technical:15, billing:5}`; C 0 `{billing:10,
  technical:7, sales:3}`; C 1000 `{billing:11, technical:7, sales:2}`; C 2000 `{billing:11,
  technical:8, sales:1}`; C 4000 = B 1.0; C 7000 `{technical:15, billing:2, sales:3}`.
* So the deepest diagnostic cell (C 7000, 0.450) **equals** the majority-class rate but is **not**
  prior collapse to one label — it is a strong `technical` bias (15/20) that happens to yield 9
  correct. The same 15/20 `technical` bias appears at B 0.25/0.50/0.75 and C 4000, i.e. across every
  cell above ~1000 tokens, while a *fully* constant answer appears only where the request is absent
  (the baseline's truncated cells — no diagnostic cell is constant). That distinction is worth
  keeping: "0.45 = majority class" is true of the number, not of the behaviour.

### 3.5 Check 5 — leakage, by content

**No leakage.** Checked from the strings, not the variable names (`experiments/V-001/logs/leakage_detail.log`):

* `REQUESTS`, `FILLER` and `QUESTIONS` are **identical** across `orch-baseline/run.py`,
  `orch-diagnostic/run.py` and upstream's `bench_long_context.py` (AST literal comparison) — so the
  two scripts under verification grade the same items and there is no train/eval split to leak across.
* No needle is a substring of the filler, and the filler is not a substring of any needle.
* The only words shared between any needle and the filler are the stopwords `for`, `the`, `and`;
  **zero content words** are shared (longest shared word n-gram = 1 over all 20 needles).
* No gold label (`billing`/`technical`/`sales`) appears in the filler text.
* Token-level overlap with the filler vocabulary is 0–5 tokens per needle, all high-frequency pieces.
* The needle appears **once** in each document — the filler is the only repeated text.

### 3.6 Check 6 — is the reported `n` the number actually scored?

**`n = 20` is genuine in every cell, but the baseline's 10 rows contain only 6 distinct model inputs.**

* Both scripts iterate the 20 `REQUESTS` and score one prediction each; `repeat.py` records arrays of
  length 20, and the diagnostic's `per_item` lists are all length 20. ✅
* `experiments/orch-baseline/results.json` has no `per_item`, so this could not be checked from the
  artifact — it required the re-run.
* **Distinct inputs per baseline row (sha256 of the exact retained state tokens):** `limit=1024,
  pad=0` and `limit=8192, pad=0` share all 20 hashes (same inputs, same dtype → same measurement).
  `limit=1024, pad ∈ {1000,2000,4000,7000}` share **one** hash, `a7ce1e314bdc225a`, for all 80 rows.
  The four `8192/pad>0` cells are each distinct. Effective independent inputs: **6, not 10.**
* Worse, that shared hash equals the state of the **same filler document with the request removed**:
  `request_absent_from_model_input: true` for all four cells (GPU-free proof, `measure.json`). The
  978 retained state tokens are 5 wrapper + 973 filler; the request starts at document token 1000
  (baseline: 1001), i.e. **27 tokens past the end of the retained region** (28 in the baseline).
* `limit=1024, pad=0` is a real measurement (document 12–25 tokens, fully visible) and correctly
  scores 0.950.

**Therefore** the flat "0.35 for every document ≥ 1000 tokens at max_len=1024" (plan.md:45,
progress.md:82, progress.md:198, P1-mechanism.md:78) is one constant-answer measurement on
request-free input, reported four times with `n=20` each. It is a **no-evidence floor**, not a
long-context floor. It is also below the trivial constant-`billing` baseline (0.45) — which
progress.md:103 already notes. Filing: **#7**.

## 5. What I did **not** verify

* **The truth of the mechanism** (attention dilution, 8 long-range hops). I verified that the numbers
  and the per-item behaviour are as reported and that the architecture description is a correct
  reading of the config; I did not test the causal story, and P-a/P-b (h2h3-knobs) are separate runs.
* **Upstream's numbers as a reproduction.** `fork/research/results/long_context_multilingual.json` is
  a foreign artifact (mps, torch 2.14, laya 0.3.18) and I did not re-run it. I used it only as
  corroboration that the constant-`technical` collapse at `limit=1024` also appears there.
* **Latency.** Excluded by the tolerance above; my numbers are 1.07×–1.40× the stored ones because the
  box was shared with other agents throughout.
* **`experiments/orch-diagnostic/run.py` was run with `pad=4000, frac=1.0` under all three dtypes,**
  which is what probe A does; I did not test other dtypes (e.g. fp64) or other checkpoints.
