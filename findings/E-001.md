## 2. What the harness is

`env/venv/bin/python experiments/harness/run.py --preset <preset> --device cuda --checkpoint
models/multilingual` is the whole interface. It builds needle-in-haystack documents, runs the
shipped checkpoint through `laya.load` / `Agent.predict`, and writes raw per-item JSONL. It takes
the GPU lock itself (non-blocking `flock` on `.gpu.lock`), gates on free host RAM and free VRAM,
and never modifies `fork/`.

Parameterised by `--pads`, `--positions` (needle position as a fraction of the filler),
`--max-lens`, `--head-max-lens`, `--n`, `--seed`, `--device`, `--languages`. `default` in a
max-len list means *do not override* — use what the checkpoint ships (1024 / 256 here).

Per item it records: item id, label, language, template, prediction, probability vector, needle
position, pad, `state_tokens_full` / `state_tokens_kept` / `input_tokens`, **how many request
tokens survived truncation**, latency, and `doc_sha256`. The document text itself is not stored; it
is regenerated exactly from `(pool, seed, item_id, pad, position)` and the hash is re-derived by
the checks.

Pools: `balanced-v1` (3 labels × 9 languages × 3 templates, one shared numeric slot pool),
`filler-v1` (30 office-logistics sentences, no digits, no support-domain vocabulary), and
`upstream-multilingual` (a verbatim transcription of upstream's `REQUESTS` / `FILLER` /
`QUESTIONS`, re-verified against the upstream script with `ast.literal_eval` at manifest time).
The filler/needle disjointness check passes (`content_word_overlap: []`, `stem_hits: []`).

The balanced draw fixes **both** marginals exactly — label `n//3`, language `n//9` — so a constant
answer cannot exceed ~1/3 on any cell and language carries no label signal. (The upstream pool is
knowingly imbalanced at 9 billing / 7 technical / 4 sales; its majority-class figure is reported in
every cell of its summary.)

**Cost note (measured).** Document construction is `O(pad^2)` in tokenizer calls: `_filler_exact`
re-tokenizes the whole accumulating filler on each appended sentence. The n=200 sweep took 1 486 s
wall, of which roughly 1 100 s was filler construction (dominated by pad=7000) and about 100 s was
model compute. It is deterministic and exact — the balanced pad hits its token budget to the token
(`pad_exact: true`, `filler_tokens_actual` = 2000/4000/7000 exactly) — but any future large sweep
should build filler incrementally in a versioned way, because changing the construction changes
every document hash and therefore every result.

## 6. Mechanism: what the 1024-token window does to the document

Measured diagnostics (the keep-length comes from the library's own `build_sequence`; every row's
`trunc_rule_ok` is true, i.e. the observed keep-length equals `min(len(state_ids), max_len − head −
1)`, the rule `laya/common.py` documents for string state). With `max_len=1024`,
`head_max_len=256`, the prompt head measures **45 tokens**, so the state window is
`1024 − 45 − 1 = 978` tokens.

* Balanced arm: the filler is built to an *exact* token budget, so at pad=1000 the request starts
  at token 1000 > 978 and nothing of it survives — total collapse from pad=1000 on.
* Upstream arm (*derived*, then measured): the filler is one sentence repeated
  `round(pad / 43)` times, and because BPE merges across the repetition boundary the real cost per
  repetition is ≈ 42 tokens. At pad=1000 the composed state is 983–996 tokens, so 6–7 tokens of
  each request are still inside the window; at pad=2000 the state is 1991–2004 and 0 request tokens
  survive.

Derived per-cell truncation for the 20 upstream requests at `max_len=1024` (real tokenizer, no
model), which *predicted* upstream's curve before it was re-measured:

| pad | state tokens (min–max) | request tokens (min–max) | request tokens kept (min–max) | rows fully kept | rows with none kept | upstream published accuracy |
|---|---|---|---|---|---|---|
| 0 | 12–25 | 12–25 | 12–25 | 20/20 | 0/20 | 0.95 |
| 1000 | 983–996 | 12–25 | **6–7** | 0/20 | 0/20 | 0.65 |
| 2000 | 1991–2004 | 12–25 | **0–0** | 0/20 | 20/20 | 0.35 |

The measured arm reproduces that exactly (§5.1): partial evidence at pad=1000 gives 0.65, no
evidence at pad≥2000 gives the constant-answer floor.

**Pre-registered prediction for §5.3** (written before that run started): with `max_len=1024` only
position 0.00 keeps the needle (`round(position × 4000) < 978`); positions 0.25–1.00 put the needle
past the window and should sit at the constant-answer rate; with `max_len=8192` (document ≈ 4022
tokens) all five positions should be readable. Measured: **confirmed** (0.750 vs 0.30–0.35 at 1024;
0.45–0.80 at 8192, no collapse).

## 7. What the numbers say

1. **The upstream baseline reproduces on this machine, exactly.** On upstream's own texts, at n=20,
   every `max_len=1024` cell matches their published 0.95 / 0.65 / 0.35 / 0.35 / 0.35, and four of
   five 8192 cells match exactly with the fifth one item apart.
2. **The 0.35 is a constant-answer rate, not a chance level.** Upstream's pool is 9 billing /
   7 technical / 4 sales, so "always technical" scores exactly 7/20 = 0.35; their raw rows at
   pad ≥ 2000 / 1024 contain one distinct probability vector across 20 different requests. On the
   balanced pool the same collapse reads 0.30–0.35 because the constant answer now has a 1/3 share.
   Chance over three answerable labels is 0.333 and the majority class on their pool is 0.45.
3. **The cause is the truncation direction, not the task.** With a 1024-token budget, an
   evidence-at-the-head document is answered at 0.75 and an evidence-at-the-tail document at 0.30,
   with 9 paired disagreements and 0 in the other direction (p=0.0039 at n=20). Every row shows the
   request's token span falling entirely outside the window in the collapsed cells.
4. **The 8192 ceiling is pool-dependent, and that is a machine-independent statement.** On
   upstream's texts this machine reaches 0.80 / 0.85 / 0.95 at pads 1000–4000 — i.e. the CUDA-bf16
   path reproduces upstream's MPS numbers. On the balanced pool the same budget reaches only
   0.55–0.70. So **the lower ceiling is a property of the balanced evaluation set (nine languages,
   fresh templates, balanced labels), not of this machine or of bf16**, and any candidate scored on
   `balanced-v1` must be reported against ~0.55–0.70, not against upstream's 0.90.
5. **At pad=7000 the model fails with the whole document in view** (0.40 at 8192 in both arms; no
   paired improvement over 1024: 1 discordant pair, p=1). This is attention dilution over long
   filler, a different defect from the truncation floor, and it is where an arm has room to win.

## 8. What this does not claim

* Synthetic needle-in-haystack only; the filler is repetitive and unlike real documents
  (`protocol.md` §10). Nothing here transfers to real long-document behaviour.
* §5.1–§5.3 are n=20 per cell: the CI there is ±0.20 and no balanced-pool budget comparison
  survives Holm at n=20. §5.5 is n=200 per cell and is the table to quote.
* The powered run covers `pad ∈ {0, 1000, 2000, 4000, 7000}` at one position; the powered position
  sweep (`experiments/position-sweep-n200`) is queued but not run.
* One item-draw seed (20240924). Whole-run repeatability is measured (identical), but seed spread
  across *different draws* is not (protocol §6).
* `L ∈ {0, 1000, 2000, 4000, 7000}` only. `L = 8192/16000/32000` was not run: the encoder's
  `max_position_embeddings` is 8192 and the baseline question is 1024-vs-8192.
* `predict_long` (upstream PR #363) is not in this checkout (`fork` @ `9fbb1ebecf33`), so protocol
  §7 baseline 6 is unavailable here.
* Latency is single-item, single-process, GPU-lock-held, but other agents were running CPU work on
  the same box; p95 is an upper bound. Latency is not comparable to upstream's MPS figures.
* No candidate intervention was applied. `fork/laya/` was not modified by this task.

## 9. Incidents

1. **A 1 GB cgroup cap OOM-killed the first real run** (my launcher, during model load; systemd
   logged `Failed with result 'oom-kill'`). The harness preflight gates on *host* memory, not the
   container cap, so it passed. Fixed by capping the wrapper at 4 GB; nothing was measured in that
   attempt. The cap used is recorded in every manifest.
2. **GPU contention.** Other agents held `.gpu.lock` for long stretches. The harness refuses to
   start (exit 2) rather than run a second concurrent job, as designed; a bounded waiter acquired
   the lock between their stages. Every reported sweep held the lock for its whole duration.
3. **`protocol.md` did not exist when this task started** (it appeared while the harness was being
   built). The harness was built to the issue text and then checked against the frozen protocol;
   the gaps found were closed: language axis including `zh`, macro-F1, random baselines,
   position-only oracle, ≥3 warm-up passes, peak VRAM, and per-cell majority-class reporting. All
   are marked in each manifest's `protocol` block, including what is *not* run (L > 8192) and what
   is unavailable (`predict_long`).
4. **Manifest defect, repaired additively.** The first two manifests did not carry the seed at top
